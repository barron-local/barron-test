# คู่มือการทดสอบ API ด้วย Postman (สำหรับนำเสนอและเก็บคะแนนกรรมการ)
**อ้างอิงตาม:** ใบประเมินการให้คะแนนการแข่งขันทักษะเทคโนโลยีสารสนเทศด้านโปรแกรมและเครือข่ายด้วยกระบวนการ DevOps (ระดับ ปวส.)  
**หมวดที่ประเมิน:** ส่วนที่ 4 ซอฟต์แวร์และการประยุกต์ (ข้อ 4.4 และ ข้อ 4.5 รวม 15 คะแนน)

---

## 🚀 1. วิธีนำเข้าไฟล์ Preset เข้าสู่ Postman (3 ขั้นตอน)

ไฟล์ทั้งหมดถูกเตรียมไว้ให้แล้วในโฟลเดอร์ `docs/postman/` หรือบนหน้า Desktop โฟลเดอร์ **`postman-devops-tnk`**:
1. **เปิดโปรแกรม Postman** ➔ กดปุ่ม **`Import`** (อยู่มุมบนซ้าย)
2. **ลากไฟล์ทั้ง 3 ไฟล์ต่อไปนี้เข้าไปใน Postman:**
   - `devops-tnk.postman_collection.json` (ชุดคำสั่งยิง API ครบทุกเกณฑ์)
   - `devops-tnk-domain.postman_environment.json` (ตัวแปรสำหรับยิงผ่าน Domain: `https://backend.mydomain.lab`)
   - `devops-tnk-localhost.postman_environment.json` (ตัวแปรสำหรับยิงตรง Local: `http://localhost:5000`)
3. **เลือก Environment ที่มุมขวาบนของ Postman:**
   - แนะนำเลือก **`DevOps TNK (Domain: backend.mydomain.lab)`** หรือถ้าทดสอบในเครื่องเลือก **`DevOps TNK (Localhost: 5000)`**

> ⚡ **จุดเด่นพิเศษ (Auto Token):**  
> เมื่อกดยิงข้อ **`1.1 Login ด้วย Admin`** ระบบจะมีสคริปต์อัตโนมัติคอยดูด Token ไปเก็บในตัวแปร `{{token}}` และ `{{admin_token}}` ให้ทันที ทำให้ข้ออื่นๆ หลังจากนั้นสามารถกด **Send** ยิงได้ทันทีโดยไม่ต้องเสียเวลาก๊อปปี้ Token มาแปะเอง!

## 🎯 3. โพยตอบคำถามเมื่อกรรมการสั่งให้ยิงทดสอบ (สถานการณ์จำลองหน้างาน)

### สถานการณ์ที่ 1: กรรมการขอดูการเข้าสู่ระบบ และการตรวจสอบ JWT Token
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.4 (1 คะแนน) และ 4.4.5 (1 คะแนน)
* **วิธีสาธิต:**
  1. เปิดโฟลเดอร์ `01. เข้าสู่ระบบ & ความปลอดภัย` ➔ เลือกคำสั่ง **`1.1 Login ด้วย Admin`** ➔ กด **Send**
  2. ชี้ให้กรรมการดู Response:
     * Status: `200 OK`
     * ได้รับ `token: "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."`
  3. (ถ้ากรรมการขอดูถอดรหัส): ก๊อปปี้ Token ไปวางที่เว็บ [jwt.io](https://jwt.io) จะเห็น Payload แสดง `username: "admin"`, `role: "admin"` และมีลายเซ็นครบถ้วน

### สถานการณ์ที่ 2: กรรมการขอดู API ดึงข้อมูลแบบส่งค่า (Query หรือ Path Parameters)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.1 (1 คะแนน)
* **วิธีสาธิต:**
  1. **กรณี Query Parameters:** เลือกคำสั่ง **`2.2 ค้นหาด้วย Query: search`** ➔ กด **Send**
     * ชี้ให้ดู URL: `{{base_url}}/api/users?search=admin`
     * ชี้ให้ดูผลลัพธ์: ตารางจะกรองมาเฉพาะคนที่มีชื่อว่า `admin`
  2. **กรณี Path Parameters:** เลือกคำสั่ง **`2.5 ดึงข้อมูลรายบุคคลด้วย Path Parameter`** ➔ กด **Send**
     * ชี้ให้ดู URL: `{{base_url}}/api/users/1`
     * ชี้ให้ดูผลลัพธ์: ดึงข้อมูลเจาะจงเฉพาะของ ID หมายเลข 1 มาแสดง

### สถานการณ์ที่ 3: กรรมการขอดู API บันทึกข้อมูลผ่าน Body (POST)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.2 (1 คะแนน)
* **วิธีสาธิต:**
  1. เปิดโฟลเดอร์ `03. ส่งข้อมูล POST Requests` ➔ เลือกคำสั่ง **`3.1 เพิ่มผู้ใช้ใหม่สำเร็จ`** ➔ กด **Send**
  2. ชี้ให้กรรมการดู:
     * Status ตอบกลับ: **`201 Created`**
     * Response แสดงข้อความ: `"บันทึกข้อมูลสำเร็จ"`
  3. เปิดตารางในโปรแกรม DBeaver หรือรันคำสั่ง `2.1 ดึงรายชื่อผู้ใช้ทั้งหมด` เพื่อยืนยันว่าชื่อ `student_demo` ถูกบันทึกลงฐานข้อมูล MySQL เรียบร้อยแล้วจริง

### สถานการณ์ที่ 4: กรรมการขอดูการอัปโหลดไฟล์ (File Upload)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.3 (1 คะแนน)
* **วิธีสาธิต:**
  1. เปิดโฟลเดอร์ `04. อัปโหลดไฟล์ File Upload` ➔ เลือกคำสั่ง **`4.1 อัปโหลดไฟล์ประจำตัวผู้ใช้`**
  2. ในแท็บ Body เลือกไฟล์จากเครื่องสัก 1 ไฟล์ ➔ กด **Send**
  3. ชี้ให้ดู Response: ได้ `status: "success"` พร้อมชื่อไฟล์ที่ถูกบันทึก
  4. เลือกคำสั่ง **`4.2 เปิดดูไฟล์ที่อัปโหลด`** ➔ กด **Send** หรือเปิดใน Browser จะสามารถดาวน์โหลดหรือดูไฟล์นั้นได้จริง

### สถานการณ์ที่ 5: กรรมการขอดูการจัดการข้อผิดพลาด (Exception Handling 400, 404, 409)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.5 (1 คะแนน)
* **วิธีสาธิต:**
  1. **ทดสอบส่งข้อมูลไม่ครบ:** กดยิงคำสั่ง **`3.3 กรอกข้อมูลไม่ครบ`** ➔ ระบบตอบกลับ **`400 Bad Request`**
  2. **ทดสอบค้นหา ID ที่ไม่มีจริง:** กดยิงคำสั่ง **`2.6 ดึง ID ที่ไม่มีอยู่จริง`** (`/api/users/99999`) ➔ ระบบตอบกลับ **`404 Not Found`**
  3. **ทดสอบข้อมูลซ้ำ:** กดยิงคำสั่ง **`3.2 เพิ่มผู้ใช้ชื่อซ้ำ`** (`username: admin`) ➔ ระบบตอบกลับ **`409 Conflict`**
  * *เน้นย้ำกับกรรมการว่า:* ระบบมีการดักจับ Error ครบถ้วน ไม่ปล่อยให้เซิร์ฟเวอร์แครชหรือตอบ Error ดิบ (500)

### สถานการณ์ที่ 6: กรรมการขอดูระบบตรวจสอบสิทธิ์และความปลอดภัย (Security 401 & 403)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.10 (1 คะแนน) และ 4.4.4 (1 คะแนน)
* **วิธีสาธิต:**
  1. **กรณีไม่ได้ส่ง Token (401):** กดยิงคำสั่ง **`7.1 ไม่ส่ง Token`** ➔ ระบบตอบกลับ **`401 Unauthorized`** (ไม่พบ Access Token)
  2. **กรณีสิทธิ์ไม่เพียงพอ (403):** กดยิงคำสั่ง **`7.2 สิทธิ์ไม่พอ (User พยายามเพิ่มคน)`** หรือ **`7.3 (User พยายามลบคน)`** ➔ ระบบตอบกลับ **`403 Forbidden`** (เฉพาะ Admin เท่านั้น)
  3. **กรณีสิทธิ์ถูกต้อง (200):** กดยิงคำสั่ง **`7.4 สิทธิ์พอ (Admin ลบผู้ใช้ได้)`** ➔ ระบบอนุญาตและตอบกลับ **`200 OK`**

### สถานการณ์ที่ 7: กรรมการขอดูโครงสร้างการตอบกลับของ API (Standardized Response)
* **เกณฑ์ที่ประเมิน:** ข้อ 4.5.6 (1 คะแนน)
* **วิธีสาธิต:**
  * ชี้ให้กรรมการดู Response ในทุกๆ Endpoint ว่าถูกออกแบบตามมาตรฐาน RESTful เดียวกันทั้งหมด:
    ```json
    {
      "status": "success",
      "message": "ข้อความอธิบายผลลัพธ์ที่เป็นภาษาเข้าใจง่าย",
      "data": { ... }
    }
    ```
